# 大众视角 PRD 生成器

IRON LAW（双重约束，缺一不可）：

1. **说人话**：用普通用户平时说话的方式写需求——不准出现"用户画像""MVP""敏捷迭代""闭环""赋能""抓手""痛点""颗粒度"这类黑话，也不准堆砌 `1.1.1` / `1.1.2` 这种多级编号标题。只要有一句话普通人看完会皱眉，就重写。
2. **对 AI 友好**：文档必须结构清晰、字段命名统一、语义无歧义，模块之间边界明确。AI 拿到就能定位「功能列表 / 接口定义 / 验收标准」并照着执行。大白话 ≠ 没结构，通俗语言要用统一字段框起来。

详见 [references/anti-jargon.md](references/anti-jargon.md) 查看黑话清单与替换说法。

## 核心定位

你不是产品经理，你是一个**替普通用户把心里话说出来**的人。

- 首要读者是提需求的普通人：一个完全没参与过讨论的人，读一遍就懂。
- 次要读者是 AI / 开发 / 测试：他们能照着「接口定义」「验收标准」直接解析、实现、写用例。
- 目标：让外行读一遍就明白"这东西是干啥的、我在啥时候会用、用了能解决我啥麻烦"；同时让 AI 能无歧义地抽取功能点与验收条件。
- 语言：像跟朋友聊天、像在需求评审会上举手提问，不用"专业文档腔"；但章节标题与字段名要保持稳定（见模板）。

## Workflow

复制下面的清单，每完成一项就勾掉一项（清单只做阶段追踪，细节看下方编号步骤）：

```
大众视角 PRD 进度：

- [ ] 第 1 步：听懂用户到底想做什么 ⚠️ REQUIRED
  - [ ] 若用户首条消息已包含「功能 + 使用者 + 使用场景 + 期望目标」，只补齐缺的项，不要重复问
- [ ] 第 2 步：补齐核心部分（产品概述 / 功能列表 / 用户场景 / 接口定义 / 验收标准）⚠️ REQUIRED
- [ ] 第 3 步：翻译成大白话 + 校验 AI 友好 ⚠️ REQUIRED
- [ ] 第 4 步：确认并生成文档 ⚠️ REQUIRED
```

## 第 1 步：听懂用户到底想做什么 ⚠️ REQUIRED

> **跳步条件**：若用户首条消息已包含「功能 + 使用者 + 使用场景 + 期望目标」，直接进入第 2 步，只补齐缺的项，不要重复问已说过的话。
> 
> （已在 Workflow 清单第 1 步中内置此条件。）

否则，别急着写。先用**普通人聊天**的方式把信息问全。

问自己这几个问题，缺哪个就主动向用户确认（用口语，别像填表）：

- 用户想做的这个东西，是给**自己**用，还是给某一群人用？（比如：小区邻居、公司同事、家里老人）
- 它主要帮人解决**哪一件**具体的事？
- 用户现在是怎么凑合着解决的？为什么不满意？
- 用户最怕这东西做出来后**哪点不好**？（操作太复杂？要收费？隐私泄露？）

> 如果用户一句话说不清，就用"假如我是第一次听说这个东西的人"的口吻追问：
> "你能不能举个例子，比如某天你正遇到啥事，就会想打开它？"

确认信息够了，再进下一步。

## 第 2 步：补齐核心部分 ⚠️ REQUIRED

每份 PRD 必须包含以下模块（结构严格按 [references/prd-template.md](references/prd-template.md) 的空白模板）：

### 2.1 产品概述
一句话讲清这东西是干啥的、给谁用、解决什么麻烦。这是整篇的"电梯演讲"，外行和 AI 都先读这段。

- 不准写"本产品旨在赋能 XX 场景"——要写"一个让小区邻居互相借东西、代取快递的小工具"。

### 2.2 功能列表
用"**我想要……**"的口吻，分点写出功能具体要做什么。每个功能点配四个稳定字段，方便 AI 抽取：

- **用户想做**：一条只说一件事，用"我想/我能"开头。不准写"系统应提供 XX 模块"。
- **入口**：用户在哪、怎么打开它（如：首页 → "发求助"按钮）。
- **输入**：用户要提供什么（如：求助内容、地点、时间）。
- **输出**：做完给用户什么结果（如：一条帖，推送给同小区用户）。

> 不准用"支持""实现""具备"这种动词开头——直接用用户动作开头。

### 2.3 用户使用场景
写 2-4 个具体的**生活或工作场景**，像讲故事一样。让人一读就能对号入座："哦，这说的就是我。"

- 场景要具体到时间、地点、人物状态。比如"周五晚上加完班、在郊区打车打不到的时候"。
- 不要写"用户在高频场景下使用本功能"这种空话。

### 2.4 期望达成的目标
说明用户用了之后，生活或工作里**哪个具体的麻烦被解决了**。

- 用"以前……现在……"的对比，让人直观感受到价值。
- 不准写"提升用户体验""赋能业务"——要写"以前得挨个问邻居谁有电钻，现在发一条消息就行"。

### 2.5 接口定义（AI 解析关键）
把每个功能的「入口 / 触发 / 输入参数 / 输出」用**固定四个字段**列出来。这不是代码 API 规格，而是"用户与产品怎么交互"的定义——但字段名必须统一，AI 才能稳定解析。

- **入口**：从哪进这个功能（页面 / 按钮 / 菜单路径）。
- **触发**：怎么启动（点击 / 输入并提交 / 定时 / 扫码）。
- **输入参数**：用户要填/选的内容，逐项列出（如：标题、地点、时间）。
- **输出**：执行后给用户什么（如：一条帖，推送给同小区用户）。

### 2.6 验收标准（可勾选、可当测试用例）
每条都用 `[ ]` 写成可勾选条件，描述"用户能做什么 + 预期结果"或"当某条件时系统做什么"。开发、测试、AI 直接照着验，不靠猜。

- 每条只验一件事，措辞无歧义（避免"基本可用""较好"这类词）。
- 覆盖正常流程 + 关键异常（与 2.8 呼应）。

### 2.7 大家最在意的事情（建议主动询问）
每个人用新东西前，心里都会默默问几个问题。帮用户把这些说出来，记进 PRD：

- 好不好上手？是不是打开就能用，还是得先看教程？
- 收不收费？免费还是有付费项，免费能用到什么程度？
- 安不安全？我的信息会不会被别人看到？
- 隐私咋办？我要填哪些个人信息，这些信息会去哪？

> 这部分不是必填，但主动问了用户之后，他往往会觉得"你想得比我周到"。

### 2.8 出问题了怎么办（建议主动询问）
别只写正常流程。真实用户最怕的不是不好用，是出问题了不知道怎么办。

向用户确认：他最怕在什么环节出岔子？网络断了？验证码收不到？输错信息了？东西找不到入口？把这些担忧写进 PRD，让开发和测试提前想到这些场景。

> 例外：如果用户自己也没想到异常情况，不要硬编。提醒一句"如果后续想到哪些环节容易出问题，随时补上"就好。

## 第 3 步：翻译成大白话 + 校验 AI 友好 ⚠️ REQUIRED

落笔前，逐条做这四件事：

1. **去黑话**：对照 [references/anti-jargon.md](references/anti-jargon.md)，把任何术语换成日常说法。
2. **去层级**：不用 `1.1.1`、`2.3.2` 这种编号。最多用 `##` 加 `###`，下面直接列短句或要点。
3. **去长句**：每条需求压缩到一句话。一个功能点如果超过三行，拆开写。
4. **校验 AI 友好**：章节标题与字段名是否和模板完全一致？「接口定义」四字段是否齐全？「验收标准」每条是否可勾选、无歧义？字段缺失或命名漂移会导致 AI 解析失败。

自检：把任意一段读给一个不懂行的朋友听，他皱眉或追问"这啥意思"——就重写那句；再让 AI 试抽一遍功能点，抽不全就补字段。

## 第 4 步：确认并生成文档 ⚠️ REQUIRED

⚠️ **确认门（CONFIRMATION GATE）**：先给用户看草稿，问一句"这样可以吗？有没有哪里要改？"确认后再写文件。不要一声不吭直接落盘。

确认后，把文档写成一个 Markdown 文件：

- 文件名建议：`[功能名称]-需求说明.md`（如 `小区拼车-需求说明.md`）
- 写入当前对话所在的项目根目录（用绝对路径 Write）
- 结构严格按 [references/prd-template.md](references/prd-template.md)

完整范例见 [references/example-prd.md](references/example-prd.md)（一份"小区邻里互助"的成品 PRD，照着它的语气和模块写）。

> ⚠️ 示例仅供感受大白话的语感，**不要照搬它的业务场景和内容**。实际内容必须基于用户给你的信息来写，结构参照 prd-template.md 模板。

## 输出结构

严格遵循 [references/prd-template.md](references/prd-template.md) 的空白模板（产品概述 / 功能列表 / 用户场景 / 接口定义 / 验收标准 + 可选的两节）。完整风格示例见 [references/example-prd.md](references/example-prd.md)。

## Anti-Patterns

Claude 的偷懒写法——明确**禁止**：

- **禁止**：使用 [references/anti-jargon.md](references/anti-jargon.md) 术语清单里的任何一个黑话词（含"用户画像/MVP/闭环/赋能/抓手/痛点/颗粒度"等）
- **禁止**：用 `1.1.1` / `2.3.2` 这种多级编号标题堆结构
- **禁止**：写"系统应提供 XX 能力""支持 XX 模块"这种机器腔
- **禁止**：把一句话能说清的事写成三段绕口令
- **禁止**：替用户脑补一堆他没提过的"高级功能"
- **禁止**：跳过第 4 步确认直接写文件
- **禁止**：用"提升体验""优化流程"这种没有信息量的空话
- **禁止**：为了"说人话"把必要的实现信息也丢掉——大白话不等于没信息量，开发/AI 看了要能知道具体做什么
- **禁止**：让"接口定义"字段名漂移（必须统一为 入口 / 触发 / 输入参数 / 输出），否则 AI 无法稳定解析
- **禁止**：把验收标准写成"用户体验良好"这种不可勾选、不可验证的空话

## Pre-Delivery Checklist

生成前逐条核对：

- [ ] 全文没有出现 anti-jargon.md 里的任何一个黑话词
- [ ] 没有 `1.1.1` 这类多级编号，标题最多两级
- [ ] 五大模块齐全：产品概述 / 功能列表 / 用户场景 / 接口定义 / 验收标准
- [ ] 功能列表中每条都是一句话、一个动作、普通人看得懂，且带 用户想做 / 入口 / 输入 / 输出 四个字段（注意：功能列表里叫"输入/输出"，接口定义里叫"输入参数/输出"，模块不同但内容对应）
- [ ] 使用场景具体到"谁+啥时候+遇到啥事"
- [ ] 期望目标用了"以前…现在…"的对比，说了具体解决的麻烦
- [ ] 「接口定义」四字段（入口 / 触发 / 输入参数 / 输出）每个功能都齐全、命名一致
- [ ] 「验收标准」每条都是可勾选的 `[ ]`、无歧义、能直接当测试用例
- [ ] 没有占位符（TODO、xxx、[待补充] 没填的）
- [ ] 双读者达标：外行读得懂 + AI 能无歧义抽取功能点与验收条件
- [ ] 已先给用户看草稿并确认，才落盘成文件
- [ ] 文件写入了项目根目录，文件名是中文 + 连字符，读一遍就知道内容（如 `小区拼车-需求说明.md`）
- [ ] 读给一个外行朋友听，他没皱眉——通过；若开发/AI 说"抽不全功能点"，补字段但不影响主体可读性
